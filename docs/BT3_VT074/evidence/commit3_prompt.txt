## 4. PHASE 2 — Triển khai Idempotent Run Completion

Sửa code để đáp ứng 5 acceptance criteria.

### AC-01 — Một run mới chỉ có một kết quả

- Tạo `run_id` khi `start_new_run()` bắt đầu một lượt chơi hợp lệ.
- ID không được dựa vào seed hoặc timestamp.
- Giữ nguyên ID khi chuyển tầng.
- Không tạo ID mới mỗi lần `finish_run()`.
- Một run được hoàn tất thành công chỉ tạo một history entry.
- Duy trì tương thích với caller `finish_run(reason)` hiện có.

### AC-02 — Retry không tạo duplicate

- Nếu cùng run ID và payload đã hoàn tất được gửi lại, trả trạng thái DUPLICATE hoặc kết quả tương đương theo contract.
- Không thêm history entry.
- Không thay đổi replay, date, last recorded run, FIFO hoặc ledger.
- Không phát lại completion signal.
- Không ghi save không cần thiết.
- Adapter phải giữ completion snapshot đầu tiên; không đọc lại globals đã thay đổi để tạo kết quả mới.

Đặc biệt: test VT74-02 của Commit 2 phải chuyển từ Expected 1 / Actual 2 thành Expected 1 / Actual 1.

### AC-03 — Hai run khác nhau được phân biệt

- Hai run có ID khác nhau nhưng cùng seed vẫn là hai lượt chơi độc lập.
- Replay seed bắt đầu một run mới với ID mới.
- Không nhận diện duplicate bằng seed hoặc thời gian.
- Không làm hỏng tính deterministic của seed.

### AC-04 — Invalid ID và payload conflict

- Kiểm tra request ID và payload hợp lệ.
- Cùng ID nhưng payload canonical khác phải trả CONFLICT.
- ID sai định dạng hoặc chưa được cấp không được chấp nhận như completion mới.
- Những yêu cầu bị từ chối không được làm thay đổi committed state, save, replay hoặc signals.
- Có boundary nội bộ rõ ràng để test có thể quan sát kết quả mà không cần xây REST API.

### AC-05 — Persistence và retry sau reload

- Persist processed IDs/ledger cùng kết quả completion.
- Khôi phục đầy đủ `run_id`, receipt, fingerprint và metadata cần thiết.
- Không mất ID vì loader chỉ đọc whitelist.
- Hỗ trợ save cũ chưa có run ID.
- Không tự suy ID cũ từ seed hoặc timestamp.
- Retention tối đa 128 processed receipts theo contract đã chốt; chỉ prune khi số receipts **> 128**, không prune ở đúng 128.
- Receipt hết retention không được làm phát sinh lại một completion cũ.
- Khi lưu thất bại, không được báo COMMITTED giả hoặc phát completion signal.
- Retry cùng pending request phải an toàn.

Kiểm tra kỹ Godot FileAccess/DirAccess API và ngữ nghĩa replace file thật trên Windows. Ưu tiên candidate snapshot, ghi tạm và xác nhận dữ liệu trước khi publish.

Không tuyên bố atomic durability, crash safety hoặc thread safety vượt quá những gì implementation và test thực tế chứng minh. Nếu storage có kết quả không chắc chắn, thực hiện chính sách fail-closed/reconcile đã mô tả trong specification hoặc báo blocker nếu chưa thể đảm bảo.
